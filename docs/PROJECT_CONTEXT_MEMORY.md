## 1. Purpose and system boundaries

PSOVA = Pakistan Society Of Vascular Anomaly. Its public, bilingual English/Urdu platform promotes education, condition awareness, care navigation, professional networking, news/events, contact and donation pledges. NVAR = National Vascular Anomaly Registry, an authenticated, consented patient and clinician registry with separate confidentiality controls. A newer PSOVA Centres Network allows approved clinical centres to manage their own patients/appointments/encounters/files/referrals/MDT/fund requests, paying annual membership. The installable mobile **web** application offers offline educational content and care navigation; it is NOT currently a native Android/iOS application and does not offer a local patient journal. Content is not clinical diagnosis, patient-specific medical advice, or a payment processor.

## 5. NVAR workflow and security invariants

Family self-enrollment or clinician-submitted case → encrypted PII + HMAC blind indexes → `PSV-XXXX-XXXX` code → pending admin review → verified/rejected/duplicate. Patients have no account. Public status lookup requires code **and** registered phone blind-index match. Clinicians register as unapproved and can submit only after approval. Admin approval/decrypted detail and CSV export are restricted and audited. Clinic-owned case is not nationally visible without explicit sharing.

PII uses per-field AES-256-GCM (`v1.iv.tag.ciphertext`), 12-byte random nonce and distinct 32-byte base64 `REGISTRY_ENCRYPTION_KEY` and `REGISTRY_INDEX_KEY`; HMAC-SHA256 indexes support exact matches only. See `lib/registry/crypto.ts`, `normalize.ts`, `guards.ts`, `patients.ts`, `audit.ts`, `schemas.ts`. No PII in logs, URLs, audit metadata, notification payloads or public output. Admin/clinician/centre role and membership enforcement must happen server-side, with audit trail for decrypts/exports. Consent and erasure/correction rights remain essential. Public stats include only verified nationally visible records, dashboard gating at **25** verified cases, primary **k >= 5** suppression plus secondary suppression to prevent reverse inference. `lib/registry/stats.ts` implements these.

**Caution:** `lib/registry/audit.ts` deliberately swallows audit-write failures (logs server error). The normative security document asks that decrypts be logged; review whether audit fail-open is acceptable for high-risk access. Source code may supersede outdated PRD statements regarding uploads: centre-specific uploads exist, whereas original NVAR v1 still has no general public upload.

## 6. Centres Network: business rules and features

See `docs/centres/PLAN.md` (implementation status says C1–C8 built). **Membership:** PKR 12,000/year (shown as 1,000/month), manual bank/JazzCash/Easypaisa/Raast transfer and transaction reference, admin verification; no integrated payment gateway. Membership expiring window 30 days; 30-day grace; beyond grace directory hidden and most operations read-only, data preserved. State computed by `lib/registry/membership.ts`, not cron; CSV owner export permitted after expiry. Roles: OWNER, DOCTOR, NURSE, RECEPTION. Role-aware guards `requireCenterMember({roles,write})` and `requireCenterApplicant`; latter supports applicant billing before approval.

Centre applications, admin approvals/tier MEMBER/ACCREDITED/EXCELLENCE, public directory profiles, certificates/QR verification, centre-owned patients by QR link or staff, secure clinical timeline, appointment booking and follow-ups (Pakistan timezone Asia/Karachi), encounters with treatment/outcome, staff management/invites, membership renewals, WhatsApp click-to-send (no official WhatsApp API), local encrypted photo/PDF uploads, per-patient NVAR sharing, inter-centre referrals and second opinions, de-identified MDT board, anonymized patient support fund and owner-only reports/CSV are represented by pages, services and APIs. Referrals create a copy in receiving centre on accept; second opinions remain de-identified/read-only. MDT teaching attachments need consent. Public support requests expose only non-identifying description, cost, centre and funding progress; contributions entered manually by admin with a public `SF-` code.

**Upload security:** `lib/registry/storage.ts` AES-256-GCM encrypted blobs tied to their storage key; `UPLOAD_DIR` must be absolute, outside deployment and `public/`, separately backed up. JPG/PNG/WebP/PDF by magic bytes, max 10MB per file, default quota 2GB/centre. Permissions: owner/doctor/nurse upload and view; owner/doctor deletion; reception no files. File read logged. **Domain state and consent are mandatory** (e.g. WhatsApp consent, NVAR opt-in, teaching consent).

## 8. API integrations and delivery behavior

`lib/server/contact-handler.ts`: validated JSON with UUID idempotency key, honeypot, 24KB cap, HMAC-fingerprinted IP rate limiting, durable ledger via `lib/server/kv.ts`, sends with **Hostinger SMTP / Nodemailer** (`lib/server/email.ts`), does not mark accepted unless mail transport accepts. Production fails with retryable 503 when `DATABASE_URL` absent. MariaDB self-creating `kv_entry`, `kv_member` tables; local fallback in-memory only. Mobile outbox queues and bounded retries (max eight) in localStorage, with foreground/network resumption. Beware of concurrency/idempotency race: `kvSet(onlyIfMissing)` return is not checked before provider send; consider atomic claim enforcement and crash recovery in future review. `lib/server/rate-limit.ts` implements read-then-write counter; concurrency may allow overshoot, worth testing. Do not log contact bodies.

`lib/server/push.ts` implements encrypted token storage and Firebase HTTP v1 publication with OAuth. It is optional and requires owner-controlled Firebase credentials, DB, encryption key and protected publisher secret. The current PWA does not implement native FCM/APNs token acquisition. Thus API existence is **not proof** of actual handset push support. Historic runbooks reference Resend/Upstash/native Firebase, but current `.env.example`, `lib/server/email.ts` and `kv.ts` use SMTP and MariaDB; prefer executable code/current deployment manual.

## 12. Non-negotiable conventions for future changes

1. Validate user input with Zod `safeParse`; server-side origin, RBAC, centre isolation, membership/consent, rate limiting, safe errors. Every relevant data decrypt/export/document read must be auditable.
2. Localization EN+UR, RTL, `next-intl` namespaces `messages/en.json` + `messages/ur.json`; do not hardcode user-facing bilingual copy. Use `@/i18n/navigation` Link/redirect/router, not plain Next navigation where locale-aware.
3. Keep Next server components default; client components only for state/interaction. `setRequestLocale` as relevant. Reuse `components/ui/*`, registry and centre form primitives, CSS token system; dark-first glass visual identity; mindful performance for animations and 3D on low-power devices.
4. Keep editorial truth flags (clinical review, Urdu review, directory verification, draft news, payment placeholders); do not silently upgrade verified/publication status. Do not insert private health data in analytics, the PWA, news or notification payloads.
5. Distinguish existing executable implementation from plan/historical PR; avoid asserting native Tauri support. No patient accounts, no hosted payment gateway, no WhatsApp sending API, no clinically enabled child journal. Respect the Hostinger shared environment and explicit manual deployment boundary.
6. Before changing critical registry behaviors, read `docs/registry/SECURITY.md` then `DATA-MODEL.md`, `API-SPEC.md`, `UI-SPEC.md`, `PRD.md` (normative precedence). `docs/centres/PLAN.md` is newer for centre workflows, and live code may incorporate documented deviations.
7. Don't merge/deploy/send notifications/charge money or modify real patient data without a specific current authorization. No credentials in docs. Focus on surgical fixes, test changes, keep main clean.
